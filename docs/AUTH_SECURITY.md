# Authentication origin and cookie configuration

Set `FRONTEND_URL` to the exact trusted frontend origin, for example `https://app.example.com`. Paths, credentials, wildcards, queries and fragments are rejected. `BETTER_AUTH_URL` identifies the backend origin. Both URLs must use HTTPS in production. Configure each permitted deployment explicitly; Vercel preview domains are not implicitly trusted.

Better Auth validates CSRF and redirects against trusted origins. Production cookies are host-only, HttpOnly, Secure, SameSite=None and Path=/; development uses HttpOnly, SameSite=Lax and Path=/ without Secure for local HTTP. CORS allows the configured frontend origin and credentials. Cookie-bearing state-changing `/api/v1` requests require the frontend or backend Origin header. A future frontend server-side proxy must preserve the trusted browser Origin for such requests; do not substitute an arbitrary client-supplied origin without validation.

Tests exercise real Better Auth and Express middleware with an in-memory adapter. `integration/auth-prisma.ts` additionally tests the real Prisma adapter against a disposable test database: set `RPF_TEST_DATABASE_HOST` and `RPF_TEST_DATABASE_NAME` to the independently confirmed test target, put its `DATABASE_URL` in ignored `.env`, then run `node node_modules/tsx/dist/cli.mjs integration/auth-prisma.ts`. The test validates the configured target and removes only its unique synthetic user, accounts and sessions. Do not use a production or development database. These checks do not verify a deployed browser, OAuth provider, proxy, or production database. Future run routes still require authorization and their own integration tests.
